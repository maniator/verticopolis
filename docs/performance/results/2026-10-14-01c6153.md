# perf:compare at 01c6153, 2026-10-14

**Snapshot of 2026-10-14, not refreshing.** One run of `npm run perf:compare` on commit `01c6153` (app 2.30.0), a pre-3.0 baseline of an engine still being cut over (#945), not release performance. The live number comes from re-running `npm run perf:compare`. Raw data (report, CSV, JSON): [verticopolis-benchmarks](https://github.com/maniator/verticopolis-benchmarks/tree/main/results/2026-10-14-01c6153) (private repository).

- Machine: cloud container, 4 logical Xeon CPUs, headless Chromium 141 (software rendering), so frame rows do not describe a real GPU.
- 10 repetitions per row, small, medium and large scenarios, 1x and 4x CPU throttle. Validation passed.

## Top numbers

Total time for a fixed run of steps, WASM over TypeScript, paired, 95% interval:

| Scenario | Bare engine, 1x                    | Bare engine, 4x                   | As the app hosts it, 1x |
| -------- | ---------------------------------- | --------------------------------- | ----------------------- |
| small    | 0.55x (0.50 to 0.79), WASM faster  | 0.60x (0.48 to 0.77), WASM faster | 4.02x, WASM slower      |
| medium   | 0.54x (0.49 to 0.61), WASM faster  | 0.71x (0.61 to 0.78), WASM faster | 3.23x, WASM slower      |
| large    | 1.08x (0.97 to 1.29), inconclusive | 1.39x (1.20 to 1.48), WASM slower | 5.45x, WASM slower      |

## What it shows

- The bare Rust engine was faster than TypeScript on small and medium and not faster on large.
- As the main-thread app hosted it, the WASM engine was 3 to 8 times slower than TypeScript, which pointed at host-side synchronization rather than the engine. Analysis: [ts-vs-wasm.md](../ts-vs-wasm.md).

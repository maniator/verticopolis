# M5 cold start, engine preload (#1254), 2026-11-04

**Snapshot of 2026-11-04, not refreshing.** Two runs of `npm run perf:compare -- --reps 10 --scenarios small --throttles 1,4` (see [benchmark-protocol.md](../benchmark-protocol.md), M5), one with and one without the engine-file preload of #1777. Run it again for current figures. The raw reports, `results.json`, CSV files and run logs are in [verticopolis-benchmarks](https://github.com/maniator/verticopolis-benchmarks/tree/main/results) (private repository) under `2026-11-04-7d1c7aea-m5-before` and `2026-11-04-7b437f90-m5-after`, not in this repo.

- BEFORE: main at `7d1c7aea` (app 2.79.0), without #1777.
- AFTER: `7b437f90`, which is `7d1c7aea` with the head of the #1777 branch (`81183d13`) merged in locally and never pushed. The two trees differ by the six files of #1777 only, so the harness and everything else are identical. Main has since taken #1777 together with other commits (app 2.79.1), which a run on main itself would mix in.
- Windows PC, Ryzen 5 5600X, full Chromium 149.0.7827.55 on the RTX 3060 (ANGLE D3D11), High performance power plan, Wine harness idle and idle CPU about 2 to 9% when checked before the first run, 6 background Chrome processes that could not be closed. The engine package hash is the same in both builds. Both trees were clean, and validation passed in both reports.
- Small scenario (729 population), 10 repetitions per engine, a fresh browser per repetition. The epsilon for M5 has not been adopted (the OD-4 calibration is open), so these are statistics, not a verdict.

Requests: in all 20 cold WASM loads of each arm (10 at 1x, 10 at 4x), `BUILD.json`, the glue and the wasm were each served exactly once. Bytes served before ready are the same (449.6 KiB wasm, 11.3 KiB glue).

## What it shows

- The preload does what it says: the engine files are requested before the main bundle and are not fetched twice.
- It does not show a cold-start gain on this machine. At 1x the paired difference moves from 83 to 76 ms with intervals that overlap almost completely; at 4x it moves from 149 to 191 ms, worse, with intervals that only just overlap (171 against 162). The warm start is level.
- At 4x the wasm fetch time in AFTER is long and very variable (median 220 ms, CV 38%, against 26 ms), which fits the engine files now competing with the main bundle for the throttled CPU and connection. That is a reading of one table, not a measured cause.
- Not shown: the medium and large scenarios, or an unthrottled network.

## Cloud cross-check, with a limited network

The PC harness limits the CPU but not the network, and the preload mainly matters when the download is slow. A diagnostic run in cloud Chromium (a `VC_TOOLING=1` build served locally, a fresh browser context per load, the same build with and without the three preload links, runs alternated between builds, 4x CPU throttling) gave these medians for the time until `window.game` exists. This is a diagnostic from one machine, not M5 evidence, and the raw numbers are not kept in the repository.

| Link                                 | Without preload | With preload    |
| ------------------------------------ | --------------- | --------------- |
| no network limit, 10 loads per run   | 961 to 1030 ms  | 971 to 983 ms   |
| 10 Mbps, 40 ms round trip, 8 per run | 3594 to 3672 ms | 3379 to 3402 ms |

The two runs of each cell are listed as a range. With no network limit the two builds are level, so the PC's 4x increase is not repeated here. Behind the 10 Mbps link the preload is about 240 ms faster (about 6%), and each engine file is still requested once. The page's `DOMContentLoaded` comes later with the preload on that link (about 1.8 s against 1.3 s) because the downloads share the connection with the bundle, while the game is ready sooner.

## Decision

Keep the preload. It does not hurt in the cloud at 4x CPU, it helps on a slow link, and the PC's 4x regression has overlapping intervals at 10 repetitions with a 38% spread in the wasm fetch time. A larger PC run at 4x, or one with network limiting, would settle the 4x question; it is not needed to keep the change.

## 2. The repo's offline and engine specs on the PC

The counts and failures below are the first run. They changed after #1815; see the dated follow-up at the end of this section's failure list.

The 35 Playwright specs for the offline start, the update, the engine integrity, repair, eviction, identity and status rows (`e2e/offline*.spec.ts`, `engine*.spec.ts`, `wasmEngine.spec.ts`) ran against the tooling build in each browser, one at a time.

| Browser                | Passed | Failed |
| ---------------------- | ------ | ------ |
| real Chrome 156        | 35     | 0      |
| Firefox 151            | 32     | 3      |
| Playwright WebKit 26.5 | 30     | 5      |

The Chrome pass includes the update rehearsal (`offlineUpdate.spec.ts`: install the first deployment, take the update prompt, then play with no network, with the old cache gone). It runs in a browser tab with the service worker, not in an OS-installed app window.

Failures, by cause (all in the test harness's assumptions, none a finding about the game, with the WebKit offline ones unresolved):

- **Chromium-only assumptions in the specs (Firefox 3, WebKit 2).** `engineEviction.spec.ts:163` expects the Chromium error text `net::ERR_...` for an unavailable page (Firefox reports `NS_ERROR_NET_RESET`, WebKit a failed `FetchEvent.respondWith`), and `engineInstall.spec.ts:105` waits for the context's `serviceworker` event, which Playwright raises only in Chromium.
- **`offlineUpdate.spec.ts:136` in Firefox.** The game started offline on the second build and hosted the engine (the spec's own checks before the failing line passed). It failed on the extra check that fetches the glue with `cache: "no-store"` and asserts `fromServiceWorker()` (Chromium only). A probe copy of the spec with those two points changed (default cache mode, no `fromServiceWorker` assertion) **passed in Firefox**, including the check that the offline start runs the second build's glue from the cache.
- **WebKit, offline reload (3 specs: `offline.spec.ts:55` and `:90`, `offlineUpdate.spec.ts:136`).** `page.reload()` with the context offline fails with "WebKit encountered an internal error" before any game check runs. The same probe fails the same way. So the offline start and the offline update are **not verified in WebKit** by this run, and Playwright's WebKit is not Safari either.
- **Follow-up (2026-11-04, #1815).** `fromServiceWorker()` is not Chromium-only: the Firefox specs that assert it pass, and the Firefox `offlineUpdate.spec.ts` failure came from the `cache: "no-store"` fetch. #1815 keeps the assertion, gives Firefox the default cache mode (and checks the text against the worker's precache entry through `caches.match`, since the default mode can fall through to the HTTP cache), and moves `engineEviction.spec.ts` and `engineInstall.spec.ts` off Chromium-only checks. On the #1815 tree (main `837575f8` plus the change), run on the PC with real Chrome 156 and Playwright's Firefox 151 and WebKit 26.5: Chrome 35 of 35, Firefox 35 of 35, WebKit 31 of 35. The four WebKit failures are offline `page.reload()` internal errors (`offline.spec.ts:55` and `:90`, and the offline steps of `offlineUpdate.spec.ts` and `engineInstall.spec.ts`). `engineEviction.spec.ts` passes in WebKit, and `engineInstall.spec.ts` now gets as far as its offline step (it used to fail earlier, on the `serviceworker` event).

## 3. CPU-throttled pass on the large tower

Real Chrome 156 with `Emulation.setCPUThrottlingRate` at 1x and 4x, the large tower seeded as the autosave (43,358 units, population 17,314), speed 3, run until 2 game days (2,880 minutes) had passed:

| CPU | Game minutes advanced | Wall time | Engine hosted | Engine error | Failure screen | Page errors |
| --- | --------------------- | --------- | ------------- | ------------ | -------------- | ----------- |
| 1x  | 2,920                 | 24.0 s    | yes           | none         | none           | 0           |
| 4x  | 2,882                 | 24.0 s    | yes           | none         | none           | 0           |

At 4x the sim kept its speed (about 120 game minutes per second). After the run the Continue button opened the game: the HUD, tool palette, bulletin and Map were on screen, with no engine failure element in the page and no repeated stop prompt. The run drove the game with the same handle the perf harness uses; no player clicks built anything.

Rust crate

verticopolis-engine is the simulation engine of Verticopolis, a tower building game inspired by SimTower (1994). This crate is the whole simulation: every rule, price, build cap, command, save format and gameplay event. It is the same engine the web game runs, compiled to WebAssembly there and linked as a plain Rust library here.

Your code owns everything a player sees and hears (rendering, audio, UI, input). The engine owns what happens in the tower. Frontends may differ; simulations may not, and the conformance suite is how a host proves it runs the real one.

Quick start

Section titled “Quick start”

These pages are also at docs.verticopolis.com, with the Rust API reference: every host call with what it does and a runnable example. The reference shows the host API only; the engine’s internals are public for its tests and hidden there.

A fuller host, which every CI run builds and runs from outside the engine, is engine-rs/consumer/.

How the engine works

Section titled “How the engine works”
  • One Simulation is one game. Start one with Simulation::new_game (or new_game_with for the calendar and bridging options), or load one from a save.
  • Commands answer instead of panicking. A command a player could make returns a result with ok and, when it is refused, a reason sentence you can show the player. Commands that move money report the amount.
  • The engine does no I/O. It reads no file, clock, environment, console or network, and spawns no thread or process. You pass in time (tick), file contents and timestamps, and you get bytes back to store wherever you like. A test in the repository holds the library to this.
  • Threads are your choice. Simulation is Send, so a native host can own a game on a worker thread, send it commands over a channel and hand frames back to the render thread. It is not Sync (it keeps internal caches it fills while you read), so one thread drives a game at a time; wrap it in a Mutex if several threads must reach it. The engine does the same work on any thread, and tests/threads.rs holds both promises.
  • It is deterministic. The same seed, the same commands and the same sequence of tick calls give the same game on any machine, in this crate and in the WebAssembly build.
  • Coordinates. floor counts up from the ground floor, which is 1; 0 and below are basements. x is a tile column from 0 across the lot. The catalog’s world record carries the exact bounds.
  • Modes. GameMode::Classic follows the 1994 original; GameMode::Modern adds facilities and rules the original did not have.
  • Pause. The simulation has no paused state: a paused frontend stops calling tick, and a build still applies while it is stopped. The catalog’s rules.builds_while_paused says whether the mode allows that. Classic does not, as in the original, so a Classic frontend refuses new placement while paused.

The host API

Section titled “The host API”

These are the calls a frontend makes, in short. The repository’s engine-rs/API.md gives each one in full; a test there names each of its calls, so a rename fails CI until that page and the example host follow.

Need Call
Start a game sim::Simulation::new_game(seed, mode), new_game_with(seed, mode, calendar, start_unbridged)
Advance time sim.tick(dt_minutes), or fixed_step::FrameStepper::advance to pace time from frames the way the web game does
Quote a placement sim.can_build(kind, floor, x), sim.can_build_transport(kind, x, bottom, top)
Player commands build, build_transport, sell_at, paint_brush (with set_lobby_height or with_lobby_height for a lobby two or three stories tall, where the mode lets that floor’s lobby rise, and refused with a reason where it cannot; its height never changes once built), add_car, remove_car, extend_transport, remove_facility, adjust_rent, set_no_rate, price_unit, change_film and book_film (show a film tier on a theater’s first screen, or on the screen named, at the price in the catalog’s films; a Modern theater runs the catalog’s cinemaScreens of 2, each with its own film, and each screen books its set_film_policy or set_screen_policy film again once its film is spent), set_ticket_price (a Modern theater’s ticket price step, from the catalog’s ticketPrices), resolve_choice
Read state the public fields (money, star, clock, tower, log) and population(); read them, never write them
Draw a frame view::structure_view(&sim) and view::ViewReader::frame, or frame::frame_view(&sim), flat number arrays read through the named slots in view::layout and frame. ViewReader::set_people_window with a view::PeopleWindow (the floors and tiles on screen) makes the frame carry only the people a view draws
A person’s trip crowd::trip::trip_facts(&person, &sim.tower) for a Person in sim.crowd.people (kept in id order, so a binary search finds one): why they are out, where the leg they are on began and where it ends, for a host’s person card. Read it while the card is open; the frame carries none of it
Gameplay events sim.gameplay.drain() after each frame; the names and payloads are in gameplay::CATALOG_JSON
Reference data catalog::catalog(mode): every price, size, cap and rule a frontend shows
Identity identity::identity(): the crate version and the save, layout, catalog and conformance versions it speaks
State hash canonical::digest(&snapshot::state_view(&sim))
Saves load::encode_simulation_vctower, load::decode_vctower, load::deserialize, import_tdt, export_tdt

Read rules, prices and caps from the catalog rather than copying them into your code. Many other items are pub so the tests can reach them; they are internal and can change in any release. Calling a per-phase step or writing a field directly skips the rules a command applies.

Features

Section titled “Features”

The crate has no default features.

Feature What it adds
conformance The harness that replays the conformance suite (scenario, suite, the .TDT referee) and the command-line tools. It reads the suite’s files, so a host turns it on only to prove conformance.
wasm The JavaScript binding, for a wasm32-unknown-unknown build through wasm-bindgen. A native host leaves it off.
tooling The binding’s test and tooling calls (raw edits that skip the game’s charges, scripted events, seeding), on top of wasm. The web game’s tests and tooling build it; the game it ships and the npm package do not. A host leaves it off.

Saves

Section titled “Saves”
  • .vctower is the native save format, the file the web game imports and exports. encode_simulation_vctower(&sim, app_version, saved_at_ms) writes the same bytes the web game writes for the same game. The engine has no clock and no build name, so you pass both.
  • Loading is decode_vctower, then deserialize, then mark_founder_from_loaded_file, which keeps the status the web game gives a tower saved before build stamps existed.
  • .TDT is the 1994 SimTower format: import_tdt(bytes, filename) reads one and export_tdt(save_json) writes one, for a mode whose catalog rules.exports_to_1994 is true (Classic); a Modern tower is refused. Each elevator car’s waiting floor travels both ways as the shaft’s schedule.homeFloors.
  • A save holds the tower, not the moment. The people in the building and the elevator cars restart on load, so a loaded game does not carry on exactly where the saving game was. Two loads of the same save stay identical to each other.
  • The loader repairs. A damaged or hand-edited save is coerced the way the web game’s loader does. It refuses a file it cannot read, a save with no numeric minutes or no units list at its top level (which would otherwise load as an empty tower), and a save from a newer engine.
  • Save versions. A save is version 7 unless it holds a lobby taller than one story; then it is version 9 and carries lobbyHeights, one [floor, x0, x1, height] entry per hall, so an engine too old to build one refuses it instead of loading a one-story lobby. Version 8 gave each floor one height ([floor, height]); it loads here with that height on every lobby tile of the floor. All three load here.

Proving conformance

Section titled “Proving conformance”

The repository’s conformance/ directory is a suite of scripted games with the state hash pinned at each checkpoint (expected.json). An engine at a given version replays every scenario exactly. With the conformance feature a host replays it itself:

The suite’s files are not in the crate package yet (#893), so a host reads them from a checkout of the repository at the engine’s engine-v<version> tag.

scenario::Scenario::parse and scenario::run_scenario(&scenario, suite) replay one scenario against a copy of the suite, which is what engine-rs/consumer/ does for every scenario on every CI run.

Versioning and stability

Section titled “Versioning and stability”
  • The crate version moves with the engine’s contract: the conformance lock (simulation behavior), the save version, the frame and view layouts, the catalog, the identity record and the JavaScript binding’s declarations. A change that keeps all of these, such as a speed-up, does not raise it on its own.
  • No semver promise yet. Until the compatibility policy is written (#893), a minor version can change a call’s shape or the game’s behavior. Pin an exact version (verticopolis-engine = "=<version>") or tag and read the changelog before you move.
  • The lock is the contract. Every change to simulation behavior lands with an updated conformance/expected.json, and that diff is what you take on when you move your pin.
  • The host API above changes only on purpose, with a changelog line.

The JavaScript package

Section titled “The JavaScript package”

Each engine release also publishes this crate’s WebAssembly build as the npm package @verticopolis/engine, with builds for Node and the browser. The JavaScript package guide covers installing and calling it from JavaScript.

> **Canonical contract.** This SPEC is the complete contract for what to build, test, and validate for the overview MAP window (#343). The plan and the owner decisions live in the companion plan file; this file does not repeat them.

# Overview MAP Window

## Why

Original Windows SimTower had a small MAP window that shows the whole tower and where the main view sits, so a player can find their way around a tall tower and see its shape. Players used it for navigation and also as a canvas for deliberately shaped towers. Verticopolis has pan, pinch and zoom but no overview. Owner priority P2 (#343), reprioritized 2026-11-03 on player feedback.

## Capabilities

- **CAP-1: find the Map.**
  - **intent:** A player on desktop or phone can discover, open and close a Map window without it interfering with building.
  - **success:** The window is open by default on the desktop layout and closed by default on the phone layout, where a Map pill opens it; the layout follows the game's existing mobile media query (`mobileMq` in `src/main.ts`), so the tablet tier counts as desktop. A Map button on desktop and the pill on phone open it (the button hides while the window is open); the window's close button or Escape closes it; after a keyboard close focus returns to the Map button, and after a mouse or touch close it stays with the page, so the next Space or Enter is the game's. Only an explicit open or close is remembered, per browser and per layout class (desktop and phone keys are independent); with nothing stored, or storage unavailable, the layout default applies and the page never breaks. A closed Map stays closed on the next tower and the next visit. When a resize crosses the breakpoint, the Map takes on that layout's stored choice or its default. The onboarding tower follows the same rule, with no extra hint. With the window open, building, inspecting, panning and pinching on the world canvas behave exactly as with it closed (Playwright, desktop and phone-sized touch).
- **CAP-2: read the whole tower.**
  - **intent:** The map shows the tower's real horizontal silhouette across the full lot, every floor and basement, rooms and facilities, lobbies, and transport shafts, so the tower is recognizable and not only a height bar.
  - **success:** Every unit in `SimView.rooms`, every run in `SimView.structure` and every shaft or stairway in `tower.transports` is in the draw list at its true tile and floor in map space (unit-tested draw list), and the map paints them all. Kinds fall into groups that are distinguishable by color and by pattern, so the map reads without color vision: each room group has its own pattern, the three elevator kinds have one each, and the plain solid groups differ in lightness (table tests pin all three). Patterns are an accessibility addition to the original, which drew none (Retail capture findings).
- **CAP-3: navigate by the map.**
  - **intent:** The map shows the area the main view currently covers, and a click, tap or drag moves the camera.
  - **success:** A camera rectangle matches the visible area in map space and stays in sync after zoom, pan, resize and loading another tower. A click or tap centers the camera on that point at the current zoom, on the rectangle too (a press that never travels past the tap slop is a tap); dragging the rectangle pans without the rectangle jumping to the pointer, and a drag that starts anywhere else on the map centers the camera under the pointer from its first move past the tap slop and keeps it there (owner, 2026-11-04). All camera moves go through the existing clamp, so any point on the map is safe to click on very tall, wide or imported (TDT) towers.
- **CAP-4: one look in both game modes.**
  - **intent:** The map looks the same in a Classic game and a Modern game (owner, 2026-11-04, superseding the Classic look that copied the retail window): rooms in their facility colors and patterns, in the banded crop fitted to the built tower, with shafts drawn as blocks. Nothing in the map's drawing (its colors, patterns, crop and view mark) reads the game mode. Which tabs the window offers may still depend on it: Traffic and Occupancy are Modern-only tabs (Decision log, 2026-11-03 parity).
  - **success:** The style table maps every `FacilityKind` to a group (an exhaustive record, so a new kind is a compile error). Rooms use the facility colors from `FACILITY_PRESENTATION`, a pattern per room group, and the shafts (stairs and escalators included) their own colors kept apart from the room colors, each as a block as wide as the shaft. A kind unknown at run time paints as a placeholder and never throws. The view mark is a solid white outline over a dark halo. The retail window's look (flat gray silhouette, fixed whole-lot scale, 1 px elevator lines, inverting dotted view mark) stays recorded under Retail capture findings as history only.
- **CAP-5: accessible.**
  - **intent:** Keyboard and assistive-technology users can open and use the map.
  - **success:** The map is focusable; arrow keys move the camera by a quarter of the visible span (the whole span with Shift), and Home and End move it to the top and the bottom of the map (the camera's center is the focused point, so Enter and Space have nothing left to do), and Escape closes the map; with the map focused it keeps every game key except zoom, the speed digits, Tab, Space (the world's pan key) and shortcuts, so nothing is built or bulldozed behind it, and a press anywhere else takes focus off it; the canvas has an accessible name and a text summary (floors above ground, basements, where the camera is); targets are at least 44 CSS px on touch; the map does not cover the build controls on a phone. On a phone the open map is a card at the top-left of the world view, inside the safe-area insets, about 150 CSS px wide and capped at about half the world view's height (portrait and landscape), below the Floor heatmap legend while a heatmap is on; the world view stays pannable and pinchable with the card open. On desktop the open map never covers the sidebar, the Floor heatmap control or its legend, or the tool palette (bounding-box checks at the smallest supported desktop size and at 1280 by 720).
- **CAP-6: cheap.**
  - **intent:** The map costs nothing when closed and little when open, even on the largest tower.
  - **success:** The draw list is rebuilt and repainted only when the identity of `SimView.rooms`, `SimView.structure` or `tower.transports`, or the layout, changes (not on `tower.revision` alone: a host can repeat a revision over other units, #1296), and a resize repaints at most once per animation frame; the camera rectangle updates from a dirty check on camera position, zoom and viewport size with no tower scan. On the `large` fixture (about 43,000 units, about 2,900 rooms) a rebuild of the draw list stays under a documented budget in CI, and the map's own cost on a large tower (open, an unchanged open frame, a camera move, a closed frame) stays under the ceilings in `e2e/overviewMapPerf.spec.ts` (S4). On a build that carries the preview flag's removal (S5 or later), the paired map-open versus map-closed frame-time and long-task measurement shows no regression beyond noise (ten or more repetitions through the existing perf harness on a GPU machine: `npm run perf:worker -- --aa wasm --map-ab --scenarios large --viewport 1280x800`, whose two slots differ only in the stored Map choice), since open is the default desktop state the Performance gate measures. The cloud has only a software renderer, which the harness refuses for a protocol run, so the run is the owner's on the PC; S5 ran the harness's `--quick` smoke in the cloud. Hardware claims come only from a real PC run.
- **CAP-7: read-only.** This holds for v1 (S0 to S5). S7 amends it with one read-only engine query for the Eval and Pricing views, `roomTiers` (see "Engine export for the Eval and Pricing views (S7)"), and the crate bump a new port member takes.
  - **intent:** Rust stays authoritative. The map invents no gameplay rule and changes no save.
  - **success:** The map code reads `SimView` and `src/presentation/`, and for the Eval and Pricing views the rooms' tiers through `RoomTierReader` (`src/simport/roomTiers.ts`), where the engine decides every tier and the map compares no score and no price. It imports nothing from `src/engine/` at run time (type-only imports of shared types follow wherever those types move), calls no engine command, and adds no catalog change and no save-format change. `roomTiers` (crate 1.19.0, view layout 12) is the only engine export the map adds. A kind's height in floors comes from the catalog the view already binds, `findViewKind(kind)?.floors` in `src/presentation/viewKinds.ts`, passed to the draw list as `floorsOf`.
- **CAP-8: player-facing text.**
  - **intent:** Players learn the map exists.
  - **success:** A Help entry, a changelog line in plain player language, a minor version bump with the lockfile, and the sidebar control formerly labeled "Map overlay" renamed "Floor heatmap".

## Constraints

- Open by default on desktop, closed by default on phone (owner decision 2026-11-03, superseding the earlier closed-by-default call for desktop). Nothing user-visible shipped until S0 to S5 were all merged (owner decision 2026-11-03): until S5 the window was built only behind a `?map` preview flag, and S5 removed the flag, so every page builds the window (`wireOverviewMap` in `src/game/overviewMapWiring.ts`), together with the "Floor heatmap" rename, Help and the CHANGELOG. The view tabs (S6 to S9) follow the same rule without a URL flag (owner, 2026-11-04): they wait in a stack of pull requests and merge together.
- Geometry is pure and testable without a canvas (S1). World constants come from `src/render/scale.ts`; the lot and floor range come from the bound view world; the whole world (`mapExtent`) matches `clampCameraY` vertically (`SKY_HEADROOM_FLOORS` of sky above the top floor, one floor of ground below the lowest floor's bottom edge), and the map's crop never goes past it vertically. Across, the crop is the lot plus the side margin (next bullet), so it reaches past the world on each side.
- The map's extent, in both game modes, is a banded crop: from one floor of ground below the lowest built floor (basements included) to the top built floor plus `SKY_HEADROOM_FLOORS`, rounded up to the next 10-floor band (bands are whole multiples of 10 floor lines, counted from line 0), at least 30 floors tall and never past the world's maximum. Across, it is the whole lot plus a margin on each side of 4% of the lot's width, rounded up to whole tiles (15 tiles on the 375-tile lot), so a tower built from edge to edge does not touch the map's sides, as the main view shows sky beside the lot (owner, 2026-11-04). The margin shows the backdrop's sky and ground, and a mark that overhangs the lot's edge (a shaft or stairway that runs past the last tile) draws into it unclipped. A click in the margin aims at a tile in it (below tile 0, or past the lot's width), and the camera clamp then moves the view's center back onto the lot, to its nearer edge (`clamp` in `towerInputCamera.ts` holds the center between tile 0 and the lot's width). The bottom keeps its one floor of ground under the lowest built floor, the same margin the camera clamp leaves under the deepest basement. The minimum grows the top, never the bottom: the top is at least 30 lines above the ground's bottom line (or the crop's bottom, if that is higher), rounded up to a band, so digging basements never lowers it. Building upward inside a band never rescales the map; crossing a band rebuilds it. The band check is constant work on every frame the map is open, with no walk over the tower, so it adds no per-frame cost that grows with the tower. A new basement moves only the bottom edge and rebuilds once. The camera clamp is unchanged and still covers the whole world, so the camera can sit above the crop: the rectangle is then clipped at the map's edge, a view entirely outside the crop shows as an edge band with a direction chevron, the text summary names the camera's floor (or the sky above the top floor), a map click moves the camera only within the crop, and dragging a rectangle that starts above the crop never pulls the camera down onto it except by the drag's own travel.
- Coordinates: tile `t` spans world x `[t * TILE, (t + 1) * TILE]`; floor `f` spans world y `[-f * FLOOR, -f * FLOOR + FLOOR]`; the camera's center is stored as `{ tile: pos.x / TILE, floor: -pos.y / FLOOR }`. A click maps to exactly that pair.
- Named facts and predicates, never bit masks or positional shorthand (CLAUDE.md). A per-kind style table is an exhaustive `Record<FacilityKind, ...>` so a new kind is a compile error.
- Map pixels are device pixels: the window sizes the canvas backing store to the layout (CSS size times `devicePixelRatio`) and applies no context scale. One pattern source per canvas.
- While the viewport rectangle is dragged the window reads the camera again for each move, since the renderer clamps the camera and the rectangle may stop short of the pointer at an edge.
- Placement (S3b): on desktop the window sits at the stage's bottom-right corner, clear of the sidebar, the palette, the toasts at the top-right and the Floor heatmap legend the renderer draws at the canvas's top-left. While it is open, the hint bar at the stage's bottom center centers in the room left of the window and wraps there, so it never runs under the window (S5). On a phone the open card sits above the Getting Started card, so a Map opened during onboarding can still be closed. On a phone the card sits at the top-left as decided, and while a Floor heatmap is on it moves down to 82 px from the world view's top, below that legend (at most 62 px tall, drawn 12 px in), so both stay readable; the rule is CSS on the picker's selected option, with no script (S5). The backdrop is a fixed dark sky over the ground that keeps the facility colors readable (the retail sky follows the time of day; v1 does not). The desktop body holds 200 by 288 CSS px (the retail window's size) wherever the stage is tall enough; on a desktop stage shorter than about 308 CSS px the window is capped at the stage height and the body shrinks, so the window never covers the controls. The phone body is 150 by 216 CSS px (CAP-5). The phone's Map pill sits at the stage's bottom-right, so a closed map covers nothing; on a 320 px phone the editor card at the bottom-left reaches it, so the pill is 44 px wide and, while the card is open, sits above it, covering only part of the card's 12 px right padding: the pill stays fully tappable (CAP-5) and no card control is covered. The inspector card and the toasts stay above the pill. S4's Playwright run checks this at 320 by 568 with the card open.
- The window is a DOM element with its own canvas inside `#stage` (plan, Architecture), outside the Excalibur render layer. New code lives in `src/render/overviewMap/` and `src/ui/`; wiring into `src/main.ts`, `src/ui/UI.ts`, `towerInputCamera.ts` and `TowerEngine.ts` (all near the 500-line ceiling) is kept to a minimal seam and agreed with the other threads that edit them.
- Visual baselines and the gallery regenerate only through the pinned image or the `pr-drift-check` approval; compare locally against main first.
- No copied SimTower art or text. The original is described in our own words with sources cited.
- Hot-path checklist (`docs/performance/hot-path-review.md`) and its section 6 record on every PR that touches `src/render/` or `src/ui/`; `/bmad-code-review` per PR.

## Non-goals

The slices that build them add the views' contract to this SPEC as they land; S7 added the engine export that Eval and Pricing read ("Engine export for the Eval and Pricing views (S7)").

## Success signal

A player with a 100-floor tower and a phone opens the Map, sees the tower's shape, taps the top and lands there in one move, and the game still builds and pans exactly as before.

## Assumptions

- The original window's drawing was measured from a retail capture (see Retail capture findings). The style table's Classic column followed those findings from slice S2b until the owner's 2026-11-04 decision gave both game modes the one look (CAP-4).
- The map's drawing box proportions are chosen in S3 from phone and desktop layouts; the geometry (S1) takes any box, so the choice changes no tested logic.

## Retail capture findings (2026-11-03)

Measured in the real game on the PC harness with five saves (TOWER1, TOWER2, TOWER5, TOWER7, MYTOWER), all four tabs each. Own-words notes only: no game bytes, screenshots or third-party text are committed. Screenshots stay in the gitignored harness folders.

- **Window.** A small fixed window at the top-left of the game desktop, about 202 by 316 px, identical at 1024x768 and 1600x1000. It cannot be resized. A thin strip about 9 px tall sits on top (no real title bar), then a row of four equal beveled buttons (Edit, Eval, Pricing, Hotel, Edit active on load), then the map body, 200 by 288 px with a 1 px gray border and no scrollbars. The body background is the same sky and ground as the main view and follows the time of day.
- **Scale.** The whole lot is always visible: 375 tiles map to 200 px (8/15 px per tile) and 120 floor slots to 288 px (exactly 2.4 px per slot). The scale is fixed and never fits the tower, so a 40-slot tower is a small stub at the bottom under empty sky and a 110-slot tower nearly fills the body. Ground sits about 10 slots above the bottom, and the silhouette runs down through the ground strip to the bottom edge.
- **Edit tab.** A flat light-gray silhouette of each floor row's built extent (setbacks and steps show). No rooms and no facility kinds are drawn; lobbies, offices, hotels and condos are all the same gray. Elevators are 1 px vertical lines at the shaft's left tile, from its bottom to its top floor: black for standard, red for service, blue for express. This was confirmed later the same day by converting each shaft's tile position in the TOWER2 and MYTOWER saves to a pixel column of the capture with an empirical fit (3 + tile times 8/15, in the capture's own pixel columns; the 3 px offset was fitted to the lines, not derived from the window's frame): every express shaft lands on a blue line and every service shaft on a red one. The remaining lines are black, so black for standard is inferred by elimination. Stairs and escalators are not drawn. Wide structures such as parking ramps show as thin horizontal bars.
- **Eval tab.** A three-swatch legend (Excellent cyan, Good olive-yellow, Terrible red) over the top of the body without shifting the map. Rooms are solid rectangles colored by score, one per room, kinds not told apart. Elevators keep their lines; lobbies and structure stay gray.
- **Pricing tab.** A four-swatch legend (High red, Average olive, Low green, Very Low cyan). Rooms are rectangles colored by rent tier. Default-priced towers are almost all olive.
- **Hotel tab.** One swatch for dirty rooms under the buttons. With no dirty rooms the map equals the Edit silhouette.
- **Camera rectangle.** A 1 px dotted outline (an inverting pen: black on light, red over red rooms, pale on a dark night sky), about 53 by 33 px, matching the main view of about 99 tiles by 14 floors. It is clipped at the map's right edge.
- **Open items.** Dirty-room coloring was seen only as a legend in TOWER1 (no dirty-room pixel captured yet). TOWER6's map tabs were not captured.

## Engine export for the Eval and Pricing views (S7)

The engine says which tier each room is in, so the views compare no score and no price (CAP-7). S8 paints the tiers; S7 adds no UI.

- **Read.** `roomTiers()` on the engine port and the binding (crate 1.19.0, view layout 12): one record with a `roomTier` row (`id`, `floor`, `x`, `evalTier`, `rentTier`) for each room that carries an evaluation or a rent level, in `SimView.rooms` order. `id` is the room's `UnitView.id`, and `floor` and `x` its anchor tile. The tier codes index the layout's `evalTiers` (`unrated`, `terrible`, `good`, `excellent`) and `rentTiers` (`unpriced`, `noRate`, `veryLow`, `low`, `average`, `high`). A room with neither (a security office, a cinema) has no row. `RoomTierReader` (`src/simport/roomTiers.ts`) reads the record by the layout's own names with no allocation per row; on an engine without the read (the TypeScript reference, which has no Map views, so the port member is optional) it answers no rows.
- **Evaluation tier.** A room carries an evaluation when the Satisfaction Floor heatmap draws it: a kind with a census population or a hotel room, with a tenant or guest present (one engine predicate serves both). The score is the satisfaction the editor shows as Eval. Terrible is under 0.4 (`VACATE_RESCIND`, the score a tenant on notice needs to stay), Good is 0.4 up to and including 0.6 (`GRIPE_WARN`: Good uses the same line as the inspector's gripe check, `names_gripe`, though the inspector names a gripe only for the kinds and tenants it inspects), and Excellent is above 0.6: the original's three swatches. A tenant on notice is rated by its score like any other. A tenant that just moved in starts at 1.0 and reads Excellent until the hourly satisfaction pass moves its score, exactly as the Satisfaction heatmap colors it, since the same predicate and the same score decide both. A score that is not a number (the loader clamps every score, so none should arrive) reads Terrible, the safe default.
- **Rent tier.** A room carries a rent level when its kind has a price in the tower's mode; No Rate is its own tier. In Classic the tier is the rung the editor's rung picker shows for the room's price (Very Low, Low, Average, High), so a default-priced room reads Average, as the retail capture's olive towers do. A Classic price that is not a finite number sits on the Average rung, where the rung picker places it. A Modern price is a band with no rungs, and its split is pending the owner's call (a decision card in the Map thread, 2026-11-04). The engine implements the recommended split, "High above neutral": a price that is not a number reads Average, the neutral reading; a price over the band's neutral price is High (the "rent set too high" gripe's own test, so +infinity reads High as the gripe does; one engine predicate, `RentConfig::over_neutral`, serves the gripe, the over-market check on a tenant's notice and the tier); a price equal to the neutral price is Average (the batch reprice's own "on the default" test, `is_neutral_price`, so a price off the neutral price by any amount is not Average, as demand and satisfaction read it); a price at or under the band's floor is Very Low; and any other price is Low. In this split Very Low is in effect one exact price, the band's floor, since the price commands clamp a price to the band, while High covers every price above neutral. The alternative on the card is "even quarters" (the band from its lowest to its highest price cut into four equal parts). There the neutral price no longer reads Average for most kinds: an office's 10,000 falls in Low (the cuts are 6,500, 11,000 and 15,500), as do the hotel rooms', the fitness club's and the clinic's, and a rental apartment's reads Very Low, so most rooms never repriced would paint Low. If the owner picks it, a follow-up engine change makes it, with its own crate bump and CHANGELOG entry. Nothing reads the tiers before S8, and the S8 pull request waits for the answer. The engine gives a rent tier to a priced room under construction, to a sold condo (by its asking price, the price the player set: in Modern the household pays a price scaled to its size, which the inspector shows as the sale price, while the condo keeps the asking price), and to a room on fire, gutted or infested (by its stored price); whether the 1994 Pricing view colors those rooms is unverified and is a PC reference check (#1619).
- **Cost.** One call across the boundary and one pass over the rooms in the engine (about 2,900 on the large fixture), constant work per room and nothing written. It adds no cache and reads the room-index memo (which refills when its key has moved). S8 reads only while the Map is open with Eval or Pricing as the selected tab, so there is no read with the Map closed or on any other tab. Its triggers are the Map opening on Eval or Pricing, Eval or Pricing being picked from another tab (one batch carries both, so a switch between the two reads nothing), a change of game hour, a move of the tower's revision or generation (a build, a removal, a load, an undo or redo), every rent command the engine applied, whichever panel sends it (today the inspector's `editorActions.ts`: `rentBatch`, `stepRent`, `noRate`, `setRent`), since the price commands move neither the revision nor the generation, every emergency answer the engine applied, since a declined bomb threat guts the rooms near it at once, with no revision or generation move, and any other applied command that changes a room's presence, score or price without moving the revision or the generation. Every trigger sets one dirty flag, which starts set (for a tab restored at boot), and a trigger raised while the Map is closed or on another tab leaves the flag set for the next open. S8 reads at most once a frame. A revision that moves during any drag that edits the tower (a build or bulldoze brush, a shaft extend, each of which moves the revision on a pointer move) waits for the end of the gesture: S8 holds revision-triggered reads while `app.undoGesture()` is open and releases them in `onActionUp` or on a cancel. The open, tab and emergency triggers hook to their edges (the open in `setOpen`, the tab pick, the answer callback), never to a per-frame test. At the top speed the game hour changes a few times a second, so reads come at most that often, plus one per applied rent command or emergency answer, within the once-a-frame bound.
- **Notes for S8.**
  - Build one `RoomTierReader` per app, on the app's port (`GameApp.enginePort`). That port is one engine object for the page life: a load, a new tower, an undo or redo restore and a `.TDT` adopt swap the tower inside it, and the layout the reader parsed stays valid.
  - Match rows to rooms in lockstep (the rows are a subsequence of `SimView.rooms`, in its order) or through one id-to-index map built per read. Never search the rooms once per row. In lockstep, a room with no row is expected. A row whose `id` matches no room before the walk reaches the end of the rooms stops the walk there, since a revision number can repeat (#1296): the rest of the batch matches through one id map built then, and a row the map does not find is dropped. Read the tiers after the view sync.
  - Drop a held batch on any swap (a load, a new tower, an undo or redo restore, a `.TDT` adopt), after `followSwap`, and read again after the swap: a loaded or new tower has new room ids, and an undo or redo changes rooms in place.
  - An evaluation moves on the hourly satisfaction pass, but a rent level moves on a player's price command and a room built since the last read has no row until the next one. A read on a change of game hour alone would show those up to one game hour late, and with no bound while the game is paused, where players usually reprice. So S8 also reads after every applied rent command or emergency answer and when the revision or generation moves (the Cost bullet's triggers), and an evaluation is then at most one game hour late, which S8 documents.

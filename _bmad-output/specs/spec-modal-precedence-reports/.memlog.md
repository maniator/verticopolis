topic: Modal precedence for the import/export fidelity reports (GH #658): make a refused report visible, and let it displace a modal that owns nothing
updated: 2026-07-28T21:06
---

- (event) Created from a bmad-party-mode roundtable held and owner-ratified 2026-07-28, plus implementation reconnaissance of the modal controllers. Rich structured input, so express distill with no elicitation.
- (note) The defect (GH #658): showImportReport and showExportReport both guard on ui.isModalOpen() and report the refusal with ui.toast(). A <dialog> renders in the browser TOP LAYER, above every z-index on the page, so that toast is unreadable BY CONSTRUCTION: it can only fire when an open modal is guaranteed to be covering it. The message's entire content is what-to-do-next, delivered where nobody can read it.
- (note) Reachable sequence: title screen, Load Tower, Choose file (the picker closes itself and the OS picker opens), pick a .TDT, FileReader reads asynchronously while the page is interactive again (seconds on an Android cloud provider), player reopens Load Tower, the read completes, the report bails and toasts under the reopened dialog. The picker re-renders looking identical and a fully parsed tower is discarded with no feedback. Pre-existing: the same race is reachable from the in-game saves manager, which also closes itself before handing off to the file picker.
- (decision) REJECTED displace-unconditionally: openModalTemplate calls replaceChildren(), so displacing showEventChoice ERASES it mid-flight and its fire-once onResolve never runs, while frameLoop.ts holds the sim frozen on shownChoice. Deadlock with no dialog and no way out.
- (decision) REJECTED an unbounded queue: the import report closes over a fully parsed Simulation, so holding it across a tower swap or a second import eventually adopts the WRONG tower, or ambushes a player who has moved on.
- (decision) REJECTED refuse-but-visible as the WHOLE answer (it remains the fallback): by the time the report is refused the file is already read and parsed, so making the player re-pick from cloud storage discards completed work. The problem is not missing data, it is a successful parse thrown away because a window was in the way.
- (decision) RATIFIED (owner, 2026-07-28): split the guard into 'a modal is open' vs 'a modal owns a pending decision or unsaved work'. Over a DISPLACEABLE modal the report takes the slot (owner chose this over wait-until-closed and over an in-place prompt): those dialogs own nothing, and the player already asked for the import by picking the file. Over a PROTECTED modal the report waits on a short leash tied to that specific dialog resolving. On a broken leash the parsed tower is DROPPED and the player is told plainly somewhere visible (owner chose this over holding a Simulation behind a new re-entry chip, and over dropping silently, which would reproduce the defect at a different moment).
- (constraint) REFINEMENT from implementation reconnaissance, NOT from the room: classification must FAIL SAFE. A modal is PROTECTED unless it declares itself displaceable, rather than the room's implied enumeration of dismissible ones. Driver: showElevatorScheduleDialog carries a dirty guard that preventDefaults Esc while the player has unsaved schedule edits, so it owns real work without owning a pending resolution, and a hand-maintained dismissible list would have missed it. With the inverted default, a dialog added later defaults to protected and the cost of forgetting to classify it is a wait rather than lost player work.
- (constraint) Visible cannot mean a toast while a dialog is open, at any z-index: the top layer always wins. Visible means either inside the dialog that is in the way, or after the way clears.
- (constraint) Export shares the fix: showExportReport carries the identical isModalOpen guard and the identical invisible toast.
- (constraint) BINDING testing rule from the room (Grumbal, seconded by Boundary): a test must assert the PLAYER IS INFORMED, not that a code branch was taken. 'We called toast()' is not the same claim as 'the player was told', and this bug is the proof, since it shipped precisely because the failure is only reachable from the state that conceals it.
- (capability) CAP-1 a refused or deferred report always reports itself where the player can actually see it.
- (capability) CAP-2 the modal guard distinguishes open from owning-pending-work, and defaults to protected.
- (capability) CAP-3 a report displaces a displaceable modal and opens immediately.
- (capability) CAP-4 over a protected modal the report waits on a leash tied to that dialog resolving.
- (capability) CAP-5 a broken leash drops the parsed tower and says so visibly.
- (capability) CAP-6 the export report behaves identically to the import report.
- (event) Self-validate pass 1 (coherence): all six capabilities carry intent and success; intents state WHAT; every constraint rules something out; non-goals present; success signal is demonstrable; ids stable. PASS. Pass 2 (preservation): every load-bearing claim from the roundtable and the reconnaissance is in the kernel (top-layer mechanism, the reachable sequence, the three rejected designs, the fail-safe classification, the leash bound, the export parity, the testing rule). PASS.
- (event) Spec PARKED, not abandoned: the room sequenced the dialog-actions visibility fix first (real data loss) and this second (P3 race), and this spec deliberately adopts that work's dialog-owns-pending-work seam instead of defining a competing one.

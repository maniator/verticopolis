topic: Fix the event-log toast/bulletin pump freezing after 200 log entries (a thief cosmetic plays with no log/toast line)
updated: 2026-07-06T21:59
---

- (direction) Backlog P2 event-visuals: 'thief cosmetic can play with no matching log/toast line' (player-reported). gds lane (touches src/engine). A repro-first investigation found the real bug is general, not thief-specific.
- (decision) Root cause: Simulation.emit caps the log at 200 via push+shift, pinning log.length at 200. UI.renderLog diffs 'new entries' off log.length ('if length===lastLogLen return'), so once both hit 200 it early-returns forever — no more toasts, bulletin never re-renders. Cosmetics (thiefFx.seq) use a monotonic counter on a separate render path and keep playing → FX with no log/toast.
- (capability) CAP-1: toasts and the event-log bulletin keep working past the 200-entry cap. success: after >200 emits, a subsequent good/bad emit still produces a toast AND re-renders the bulletin.
- (capability) CAP-2: the fix is general to all events (any good/bad emit toasts regardless of session length); the thief cosmetic and its log line can no longer diverge. success: a thief event after 200+ prior events shows both its cosmetic and its log/toast line.
- (decision) Fix: add a monotonic Simulation.logSeq incremented on every emit (never decremented by the 200-shift); UI.renderLog diffs on sim.logSeq, not log.length, and clamps the fresh count to [0, log.length] (older entries were shifted out).
- (constraint) logSeq is a transient UI-diff aid: engine-pure (no DOM), and NOT serialized — the log itself isn't serialized, so both reset to 0 on reload.
- (constraint) On a tower swap (adoptSim: load/import/new-tower/undo/redo), reset the UI log baseline to the new sim's logSeq and refresh the bulletin — else the stale baseline skips or spams toasts for the new sim (secondary bug the investigation flagged).
- (constraint) Preserve existing behavior: only 'good'/'bad' entries toast; the bulletin shows the last 40; the log stays capped at 200.
- (note) Non-goals: not changing the thief cosmetic itself, the 200-cap size, or which kinds toast; no post-reload toast replay (the log isn't persisted, so a reload starts clean).
- (direction) User (BMad) expanded scope after a game/UX/architect party: the bulletin is too short (only 40 of 200 shown) for scrollback, and must NEVER stop adding at the cap, and must NOT crash a slow phone with too much DOM — make the perf ceiling a first-class spec constraint.
- (decision) Party verdict: don't auto-clear and don't build a separate alerts channel (over-engineering for an ephemeral surface). DO turn the bulletin into a bounded rolling window: APPEND newest + PRUNE oldest so it never freezes and never grows unbounded. #log is already overflow-y:auto + column-reverse (auto-pins to newest), so scrollback is CSS-ready — only the 40-render and the per-frame innerHTML rebuild were the gaps.
- (decision) Render via append + prune, NOT per-frame innerHTML rebuild (rebuild is the mobile killer and resets scroll during review). New lines are createElement+textContent (auto-escaped, safer than the old escapeHtml+innerHTML). Buffer cap and DOM cap both 300 (~a session; ~100 bytes/entry; 300 light divs is safe).
- (constraint) PERFORMANCE (BMad, first-class AC): the rendered DOM node count is held CONSTANT at LOG_DOM_CAP (300) — a long session can never grow the log big enough to jank a slow phone. Tested: childElementCount ≤ cap after 1000 emits.
- (note) Deferred to its own ticket (event-log-persistence, P3): serialize a bounded log tail so scrollback survives the reloads this game does to itself (GPU-context-loss recovery, PWA update). Save-size tradeoff.
- (constraint) Toast burst cap: renderLog fires at most TOAST_MAX(=5) toasts per frame (the newest good/bad of the batch); a catch-up tick flushing up to LOG_DOM_CAP lines must not spawn hundreds of transient toast nodes+timers. The bulletin still records every line. (gds-code-review Blind+Edge Case Hunter finding #1/#2, burst flood.)
- (constraint) renderLog appends the bulletin line BEFORE calling toast(), and wraps toast() in try/catch: the bulletin is the durable record, so a throwing toast must never drop a line or stall the rest of the batch. Slice via log.slice(length-fresh) with an explicit fresh<=0 return, never slice(-fresh) (-0 would re-render the whole buffer). (gds-code-review Edge Case Hunter finding #1, slice(-0) hazard.)
- (event) gds-code-review ran (Blind Hunter + Edge Case Hunter). Both surfaced the same two findings: slice(-0) whole-buffer re-render and burst toast flood. Both patched (slice(length-fresh)+fresh<=0 guard; TOAST_MAX=5 per-frame cap; append-before-toast with try/catch). Edge Case Hunter verified column-reverse order, scroll, mobile cap, resetLog-on-swap, and DOM-bounded-at-300 all clean. Pre-existing toastTimers leak deferred to backlog P3.

# Decision log: title-screen Load Tower

Run: `ux-verticopolis-2026-07-28`. Scope: the splash action stack and the
load-only tower picker it opens. Not a full visual-identity spine (the
`ux-verticopolis-2026-07-07` run is likewise scoped, to responsive layout).

Discovery input was a `bmad-party-mode` roundtable held 2026-07-28 (Sally UX,
John PM, Samus Shepard, Link Freeman, with Grumbal and Boundary summoned from
the review crew, plus Mo the phone player as a walk-on). Its outcome and
supporting rulings are in
`_bmad-output/party-mode/memories/installed/.memlog.md`. The owner ratified the
landing and the button order the same day. Entries below are the decisions that
bind; the spines distill them.

## D1. The problem is missing reach, not a missing feature

`appBoot.ts` computes `hasSave` from `app.hadReadableSave`, which
`SaveGame.loadResult()` derives from two localStorage keys only: `verticopolis-save`
and the legacy `simtower-clone-save`. Manual slots 1 to 3 are never consulted at
boot, and `SaveGame.listSlots()` is reachable only from inside a running game.

Two players are stranded by this today:

1. **Corrupt autosave, healthy manual slot.** `hadReadableSave` is false, so the
   splash renders New Tower alone while a readable tower sits in slot 2. The
   only route back is founding a tower the player does not want, then opening
   Saved Towers from inside it. The existing corrupt-save copy ("Starting a new
   tower") is true but incomplete in exactly this case.
2. **Fresh install or new device.** localStorage is empty but the player holds a
   `.vctower` export. Import lives behind the same in-game dialog, so the same
   throwaway tower has to be founded first.

Both are reachability failures of the title screen. The new action closes both.

## D2. Not the in-game Saved Towers dialog

Rejected: mounting `showSaves` / `savesTemplate` on the splash.

Those rows carry **Save** and **Delete**, and the footer carries **Export to
file**. On the splash the live simulation is the throwaway boot sim
(`main.ts`: `this.sim = boot.sim ?? Simulation.newGame(...)`), and the codebase
holds a standing invariant that nothing may mutate the sim while the splash is
up: `saveLoad.ts` states it in the `saveBeforeUpdate` comment, and the 30 second
autosave timer enforces it by checking for `#splash` before every tick.

A Save button there would not merely be wrong, it would succeed quietly.
`saveToSlot` stamps `app.sim.view = app.engine.viewState()` first, and the
splash engine is paused but alive, so the call returns normally and writes a
slot full of nothing carrying a genuine timestamp. Export would hand the player
a `.vctower` of a tower they never built. Delete sits one tap away on a phone.

## D3. Not the file picker alone

Rejected: routing the action straight to `openImport`.

Slot saves live in localStorage, which no OS file picker can see. The most
common returning player would be shown their Downloads folder and none of their
towers. `.vctower` is also the least reliable surface shipped: `openImport` sets
`accept` to `.vctower,application/octet-stream,.tdt,.TDT`, and the
`application/octet-stream` entry exists specifically to stop Android pickers
greying out an extension they do not know.

## D4. Ratified: one action, one surface, two sources

**Load Tower** is a single splash action opening a single load-only surface. That
surface lists the device slots (auto plus 1 to 3) and carries **Load from a
file...** as a row in the same list. The player picks a tower, never a storage
mechanism. Where a given tower happens to live is the game's problem.

## D5. Ratified: order is Continue, Load Tower, New Tower

New Tower is the only action on the screen that can cost the player something,
so it sits furthest from the default focus and from the Esc and backdrop safe
dismiss. The two "your tower already exists" actions cluster. Primary styling is
unchanged: Continue keeps `.primary`, and New Tower still takes `.primary` when
no save exists, so the first-timer's eye still lands correctly regardless of
position.

## D6. The label says Tower, not Save

The product says tower everywhere already: "Saved Towers", "Tower loaded", "New
Tower". A save is a file format; a tower is the thing the player built. Mo's
line settled it: "I think of it as my building."

## D7. Corrupt-but-present slots are shown, not hidden

Presence is a raw `hasSlot` check (`getItem !== null`), never the parse-based
`listSlots().exists`. A slot that is present but unreadable renders as a
disabled row labeled unreadable rather than vanishing.

Hiding it would tell the player their tower is gone, when `preserveUnreadable`
exists precisely because a save written by a newer build may be recoverable
later. The same reasoning already governs writes in `SaveGame.ts`. An unreadable
row is also the strongest cue for the file row beneath it, since that player is
the one who most needs Import.

## D8. Empty state is one line plus the file row

With nothing on the device, the surface says a single honest line and offers the
file row. It does not render four rows reading "empty", which on a phone is a
wall of nothing.

The button itself does **not** change destination based on state. One button,
one surface, always: a control that goes somewhere different on different days
is a control nobody trusts.

## D9. The dismissal invariant

**The title screen is dismissed by a tower arriving, never by a dialog opening.**

So: no teardown when the picker opens, none when the OS file picker is
cancelled (`openImport` binds `onchange` only, and a cancel fires no event at
all), and none when a load fails or a slot turns out to be corrupt. A failed
load toasts and leaves the player on the title screen. Teardown happens on
successful adoption only.

## D10. A load from the splash re-pauses, exactly like Continue

`teardownSplash()` calls `pauseForSplash(false)`, which resumes the engine to
play speed. `onContinue` already compensates with `app.setSpeed(0)` and the
"Press ▶ to resume" toast, on the rule that the Play control is the single
resume. A load from the splash inherits that contract, or a player lands in a
running tower they have not seen in three weeks.

## D11. The picker wears the retro modal chrome

The splash is deliberately un-unified (its own box-art chrome, documented in the
`.splash-mute` and `.splash-install` CSS comments), but modals stacked *over* the
splash already use the retro `<dialog id="modal">` shell: both How to Play and
the New Tower rule-set picker do. The tower picker follows that precedent, which
also reuses the existing `.slot` row styling and inherits the `safeDismiss`
guard that stops the splash's own Esc firing underneath an open modal.

## 1. Executive summary

Verticopolis is in strong health. All four quality gates pass at the audited tip (typecheck, lint, 2,601 tests, build); coverage, e2e, and the perf gate additionally passed at the immediate pre-merge baseline and again in CI's pinned container on this PR's branch atop the tip (§4 rows 8-14). Production serves exactly the audited commit with zero runtime errors in 7 days and zero crash telemetry in 30, all 16 real owner save files import and round-trip byte-stable through the production code path, and the Classic/Modern rule split, transport-pool canon, migration chain, and engine determinism all held up under directed inspection. The application source (`src/`) carries zero TODO markers and its process discipline (mandatory adversarial reviews, a mirrored backlog, guard tests) is unusually deep.

The audit found no P0 issues. It found one P1 and a cluster of P2s in four themes:

1. **Big-tower performance is now an engine-CPU problem, and one specific defect dominates**: the render loop calls the un-memoized spatial congestion rebuild every frame (AUD-014), a full O(units) scan at ~60 Hz that explains most of the measured 11 -> 5 -> 2 FPS scaling on real saves. Behind it sit measured per-tick and hour-boundary scan costs (8.6 ms / 53 ms at 25k units; AUD-015/016/017) with named fixes.
2. **Two save-integrity gaps** (AUD-010 silent quota failure on manual saves, AUD-011 forged-save unit overlap), both small fixes in established patterns.
3. **Process debt**: the backlog/issue mirror has drifted in both directions and ~90 review deferrals sit untriaged and invisible to it (AUD-002/003/004).
4. **CI supply-chain hygiene** (mutable action tags, persisted write credentials in baseline workflows; AUD-027/028) and **mobile planning-reality divergence** (stale PUBLIC_REF, docs describing absent CI, an analytics marker nothing consumes; AUD-019/035/036/037).

Counts: **P0: 0 · P1: 1 · P2: 12 · P3: 23 · Opportunity: 2** (38 findings, every one carrying evidence and an existing-issue disposition). The remediation plan (§18) is deliberately incremental; nothing here calls for a rewrite.

## 3. Repository and architecture overview

Verticopolis is a from-scratch, browser-native SimTower (1994) clone: TypeScript on Excalibur.js, built with Vite, lit-html UI, Tone.js audio, deterministic DOM-free engine (`src/engine/`, seeded `rng.ts`) with strict layering (engine / render / ui / game controllers / storage / platform). Persistence is localStorage slots plus a compressed `.vctower` export container and a binary `.TDT` interop surface with the original 1994 game. Two-tier testing (vitest unit+integration with a coverage ratchet; Playwright e2e incl. visual and perf baselines), 8 GitHub Actions workflows, Vercel deployment. The BMAD/BMGD process is unusually deeply integrated: adversarial review skills are mandatory per change, deferrals flow to a curated backlog that mirrors to GitHub issues (standing rule 2026-07-15), and planning artifacts (PRD, GDDs, epics, spec kernels, party rulings) live in `_bmad-output/`.

- **AUD-010 · P2 · Confirmed · silent data-loss risk (storage)**: manual saves swallow storage failures. `SaveLoad.save()` (`src/game/saveLoad.ts:112-116`) and `saveToSlot` (`src/game/appModals.ts:71-77`) call `SaveGame.save`/`saveSlot` with no try/catch and then toast success; a `QuotaExceededError` (storage full, private mode, storage disabled) escapes as an uncaught event-handler error and the player gets no feedback at all, believing the tower saved. This is a gap, not policy: the context-loss recovery path, the update flow, and the import slot-copy all guard the same write deliberately, and `spec-save-quota-reload-hardening` explicitly scopes itself to the reload path only. Fix: catch at both sites with an honest "save failed: storage full or blocked" toast. Coordinator-verified at both call sites. Untracked anywhere. Small.
- **AUD-011 · P2 · High confidence · forged-save state corruption**: `Simulation.deserialize` (`src/engine/sim/serialization.ts:158-289`) validates unit kind, geometry, and field types but never checks unit overlap, while transports DO get an overlap pass (lines 399-423) and the TDT importer drops overlapping rooms for exactly this reason (`tdtParse.ts:133-136`: shared tiles corrupt the per-tile room index, last-wins on register, shared-tile deletes on unregister). A forged `.vctower` with two units on the same tiles loads cleanly and corrupts census, hit-testing, and removal invariants. Fix: mirror the transport overlap filter for room units. Untracked. Small.
- **AUD-012 · P3 · High confidence · load-time DoS via crafted save**: `deserialize` maps the whole `data.units` array with no count cap, while transports are explicitly bounded (`.slice(0, POOLED_CAPS...)`, serialization.ts:398, with a comment naming the load-time-hang risk). A small `.vctower` inflating to the 64MB cap can carry ~3-4M minimal units (legit towers top out near ~41k tiles), freezing the tab at load. Fix: cap units at a grid-area-derived bound before mapping. Untracked. Small.
- **AUD-013 · P3 · Confirmed · extends #340**: two more uncoerced deserialize fields beyond the `towerName`/`builtWeddingHall` pair issue #340 tracks. (a) `sim.evaluatedTower = data.evaluatedTower` (`serialization.ts:90`): a forged truthy non-boolean flows into the vipVisits backfill and TOWER-status logic. (b) Unit `completeAt` rides the `...u` spread with no `num()` coercion (unlike `vacateAt`): a forged `NaN` makes `finishConstruction`'s `minutes >= (u.completeAt ?? 0)` false forever, so the unit is permanently stuck under construction and the NaN re-serializes. Recommend editing #340's scope to name all four fields rather than opening a new issue. Small.
- **AUD-014 · P1 · Confirmed · per-frame full-tower scan on the render path**: `TowerEngine.tick()` calls `this.sim.congestion()` every frame (~60 Hz) at `src/render/excalibur/TowerEngine.ts:363`; under the default v2 sim model that is `spatialCongestionByFloor` (`src/engine/sim/congestion.ts:124-198`), which is NOT memoized and per call rescans all units with `censusCount` per unit, runs the un-memoized `functionalParkingSet` flood fill (whose own doc comment assumes it is off the frame path), and walks every transport span with an O(span x skipList) `stopsAt`. At 25k units this is the dominant per-frame CPU cost and the primary explanation for the measured 11 -> 5 -> 2 FPS scaling (which is therefore NOT purely a GPU-environment artifact). Coordinator-verified at both cited sites. Overlaps open issue #338, whose "measure first" condition this audit satisfies; the issue understates the trigger (it is the render frame, not just the sim). Fix: memoize `spatialCongestionByFloor` and `functionalParkingSet` on the existing `(revision, mealOverlayRevision, step)` key set, following the in-repo `Crowd.queueView` precedent. Recommended backlog action: raise #338 to P2-active and rewrite its acceptance criteria around this memoization. Scope: small-medium.
- **AUD-015 · P2 · Confirmed · O(units) scan per spawned person**: `pickX` (`src/engine/crowd/trips.ts:57-66`) scans the entire unit list per call; it runs twice per spawned trip plus once per dwell expiry, up to ~16 full scans per sim step at high spawn rates, a leading slice of the 8.6 ms tick. Fix: a revision-memoized floor -> structural-tile index, preserving `seed % tiles.length` ordering so spawn positions stay byte-identical. Untracked. Small-medium.
- **AUD-016 · P2 · Confirmed · ~20 full-unit scans per hourly star evaluation**: `evaluateStar` (`src/engine/sim/star.ts:13-47`) re-derives population and each star gate with fresh full scans (up to 3 ladder iterations x ~6 gates), every hour. Fix: one shared per-kind operational-count pass, or early-exit when the target equals the current star. Untracked; a named hour-boundary contributor. Small.

## 22. Final risk assessment

**Overall: LOW risk, healthy trajectory.** The project's correctness spine (deterministic engine, canon caps, migration chain, save round-trip) is verifiably solid against real data; production is current, quiet, and matches the repo. The two risks worth naming plainly:

1. **Scale risk (moderate, contained; absolutes softened by the live supplement)**: big towers degrade today (AUD-014 and friends), though on desktop-class hardware a 25k-unit tower stays playable at normal speed (~37.5 FPS median); the concentrated pain is fast-forward (~25 FPS, ~45% main-thread) and overlay use, and the audience most likely to hit it is the project's most engaged players importing real 1994-era towers. The fixes are known, small, and sequenced (§18 steps 3, 5, 6); the risk is only realized if they idle while player towers grow.
2. **Process-outrunning-itself risk (moderate)**: the review machinery generates findings faster than triage retires them (90+ inbox sections, two-way mirror drift, a planning surface in the mobile repo that overstates reality). None of this loses code correctness today; it loses _trust in the trackers_, which is the thing the whole process exists to provide. The §18 step-1 true-up plus the party's per-PR triage rule addresses it structurally.

Security exposure is low (client-only game, defensively-parsed untrusted inputs, clean prod dependency tree); the CI hardening items are preventive, not reactive. Data-loss exposure after the N-4 bundle lands is minimal. No finding threatens the parity mission or the Classic/Modern architecture, both of which this audit examined specifically and found sound.

# Story: TDT import and export in the crate

## Why

The 1994 `.TDT` format is read and written by 24 files under
`src/storage/tdt*` (parse, encode, tables, transports, tail, stamp, the
import and export reports), with 20 tests. It is engine-data work: bytes to
the serialized game and back, with hashed seeds and table layouts that must
be bit-exact, which is why the repo already reviews it as engine fidelity.
The Godot client must read and write 1994 towers natively, and the web must
keep doing so through the same binding as the engine. So the TDT code moves
to Rust, as a `tdt` crate beside the engine crate in one Cargo workspace,
held to a referee of its own. The TDT crate depends on the engine crate (for
the serialized-game shape, `jsmath` and the loader helpers), and the engine
crate has no dependency on TDT, so a tower that never touches a 1994 file
carries none of it.

## Acceptance criteria

1. **AC1 Same bytes in, same JSON out.** A `tdt` crate in the `engine-rs`
   workspace parses
   every `.TDT` fixture the TypeScript tests use to the same serialized game
   the TypeScript importer produces, pinned by a lock of canonical-JSON hashes
   generated by the TypeScript side and matched by a Rust referee command.
2. **AC2 Same JSON in, same bytes out.** Export of every fixture save and the
   referee's three `.vctower` fixtures produces byte-identical `.TDT` output
   to the TypeScript exporter, pinned by file hashes in the same lock.
3. **AC3 Reports.** The import and export reports (what was mapped, what was
   dropped, parking, part merges) match field for field; their prose follows
   the same copy-catalog rule as engine prose once that story lands.
4. **AC4 Surface.** The crate exposes import and export through the same seam
   the engine uses (bytes in, serialized game or bytes out), so the WASM
   binding and the Godot client call one function each. The WASM module gains
   `importTdt` and `exportTdt`. Because the binding module lives in the
   engine crate today and the engine crate must not depend on `tdt`, this
   story moves the binding to its own workspace member (`engine-rs/wasm/`)
   that depends on both crates; the engine crate loses its `wasm` feature
   and `scripts/wasm-build.ts` builds the new member instead.
5. **AC5 No TypeScript change** beyond adding the lock and its generator to
   the TypeScript tests; the TypeScript importer stays the reference until
   `story-engine-retire-typescript`.

## Out of scope

- The file dialogs, drag and drop, and the `.vctower` chooser; host work.
- Writing a TDT the original game never produced (new facility kinds); the
  export table rules stay as they are.

## Dev notes

- Turn `engine-rs/` into a Cargo workspace first (the engine crate keeps its
  path and name; `engine-rs/tdt/` is the new member) so `cargo test`,
  clippy, coverage and the CI job keep running from the same directory.
- Port in the TypeScript file order: byte reader and writer, constants and
  tables, parse, transports, tail and stamp, encoder, reports.
- JavaScript number semantics apply here too (`hashSeed` and the table
  arithmetic); reuse `jsmath` and the loader helpers.
- Review: `/gds-code-review`, per the TDT rule in `CLAUDE.md`.

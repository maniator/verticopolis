# Story: the scenario library, and the tests that pin what the referee cannot see

## Why

The referee proves the two engines agree on what the six scenarios drive, and
the coverage map on `story-engine-rust-port` says that is 78% of the Rust
engine's lines on its own. The dark part is specific: the events other than
fire and bomb threat, the services (VIP visit, exterminator, metro cutoff),
star evaluation branches, churn and relocation, off-shift schedules, and the
migration paths the three fixtures do not take. Code there is ported and has
never been compared. This story lights it, and sets the rules that keep it
lit.

## Acceptance criteria

1. **AC1 Playthrough scenarios.** New scenarios under `conformance/scenarios/`,
   each readable as a designer's playthrough and each aimed at a dark module
   from the coverage map, at least: a hotel weekend with housekeeping and an
   exterminator call; a VIP visit with no parking, then with parking; a star
   evaluation that fails and then passes; a metro platform cut off and
   reconnected; express cars off shift on a scheduled shaft; a condo
   relocation month; every remaining event in the roster. Each one lands with
   its lock entry regenerated by the TypeScript suite and matched by the Rust
   referee in the same pull request.
2. **AC2 Runner commands on both sides.** Every new command the scenarios need
   (`callExterminator` first) is added to `src/tests/conformance/scenario.ts`
   and to `engine-rs/src/scenario.rs` together, with the field table in both
   extended identically.
3. **AC3 Coverage floor raised.** The line floor in `.github/workflows/engine-rs.yml`
   moves up to the new measurement, and no module in the coverage table on
   the port story stays below 75% of lines.
4. **AC4 Canon constants pinned.** Rust unit tests state the numbers the
   canon section of `CLAUDE.md` protects: every per-tower build cap, the one
   24-shaft elevator pool with express inside it, the 64-link stair and
   escalator pool, 8 cars per shaft for every elevator kind, the spans.
5. **AC5 Loader table tests (#860).** Table-driven tests over the migrations
   from v1 to v7, the coercion of forged values the hand-edited-save row
   (#858) lists, and the schedule coercion, each row a small input and its
   expected serialized output. #860 closes with this story.
6. **AC6 Differential fuzzer.** A `fuzz` binary in `engine-rs` and a matching
   script on the TypeScript side generate a scenario from a seed (random
   builds, edits, ticks and events within the rules), run it on both engines,
   and compare the hashes at every checkpoint, with no lock involved. A
   divergence prints the seed and writes the scenario JSON so it can be pinned
   as a named scenario. It runs on a nightly schedule, never on the pull
   request gate.
7. **AC7 The rule.** `CONTRIBUTING.md` states: an engine pull request that adds
   a branch adds a scenario that reaches it, and the coverage step is how
   review checks it. The two-engine rules from the roadmap move there too.

## Out of scope

- Prose parity (log text, event messages); still outside the contract.
- The test-mapping table for the TypeScript engine's 360 tests; that is the
  retirement story's gate (`story-engine-retire-typescript`).

## Dev notes

- Start from the coverage map: `cargo llvm-cov` over the tests plus the
  referee, then write the scenario that reaches the largest dark block, lock
  it, re-measure, repeat. Scenarios are cheap; a scenario with no new lines
  covered is not worth its lock entry.
- The fuzzer's generator must only emit commands the field table accepts and
  the engine can refuse gracefully (a build that fails is a fine step); it
  shrinks by truncation, since the scenario format is a list.
- Review: `/gds-code-review`, since every change here is engine parity.

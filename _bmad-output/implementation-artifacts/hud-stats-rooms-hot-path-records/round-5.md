## Findings

- **F1 (new to the record; in code this PR adds; HP-1, HP-2, HP-9, HP-11, HP-12; low).** `mergeSimulationDelta` (`src/wasmhost/merge.ts` 89 to 96) marks every record the hourly delta rewrites, whether or not a counted field moved, where the full merge (`unitsMoved`, round 3's F2 fix) marks only the units whose five counted fields differ. The delta carries every unit whose save form moved, mostly fields the counts never read (satisfaction, rent, occupants), and the frames before it already carried each room's state and customers up to the last reply (a state that moved since then differs from the record and would still be marked). So the HUD read after each delta recounts every rewritten room for nothing. Entry point and tier: the worker host's reply apply (`applySaveSync` → `mergeDelta` → `mergeSimulationDelta`), per engine hour pass; the cost lands on the next HUD read (wall clock, `runFrame` → `uiStatus.update` → `stats()`), once per hour pass. At speed 3 an hour passes every 0.15 to 0.5 s against a HUD read every 160 ms, so one read in one to three pays it. Sizes and estimate (24 game hours modeled per tower, `deltamarks.out`): records per delta median 564 on `hotel-heavy`, 65 on the owner's save, 15 medium, 1 large; max 2,888 large (every room, the first hour after a load) and 1,138 owner's save; records that change a counted field median 0 to 6, max 18. The read after a delta: median 0.056 to 0.16 ms, max 0.34 to 1.08 ms, against 0.003 to 0.006 ms when only the counted changes are marked. About 5 visits per marked room (a map lookup, two tallies, the flags and the population), so up to about 14,400 visits per read on large, once per hour pass: inside HP-2's per-hour budget, which lets triage dismiss it under section 7 with this estimate. It is not section 7's always-`patch` class: the read still uses the ledger, and the marks only widen its recount. Recommended: patch, since it is about five lines in code this PR adds, it matches the full merge and Design's aim that "the read after it costs what the read after that hour's pass would", and it makes the worker host's HUD read as flat as the other paths. TypeScript equivalent: the engine marks only through `setRoomState` and its `markRoom` call sites (writes of a counted field); the full merge compares first. Remedy (HP-9 item 3, the counter's own discipline): before `assignRecord`, compare `COUNTED_FIELDS` between the held unit and the record and mark only on a difference (keep the layout compare and its drop). HP-10: compare before the write; a record with no `customersIn` against a held count differs and marks (the delete is a write); a mark is idempotent; AC4, Design and the HP-8 row say "marks every unit it rewrites" and would follow; a test that applies a delta changing only satisfaction and checks the next read recounts nothing (for example through the proxy pattern `roomCounts.test.ts` already uses), beside the existing delta tests, pins it. The delta merge itself measured 1.12x to 1.17x `main` (3.46 against 3.12 ms on a 2,888-record delta on large, 1.40 against 0.97 ms on 684 records on `hotel-heavy`), per hour, sub-millisecond. Not in any open issue.
